## 1. Objetivo
Descripción de Jira (literal): «Para que la app avance sin esperar al backend: cada spec de backend publica su contrato en la §4 y la app consume una API simulada (mocks) con esa forma de respuesta; cuando sale el endpoint real, solo cambia la URL. Se parte de los contratos que ya están en la §4 de las specs (por ejemplo /auth/firebase, /oficios y colonia por punto). No depende de TT-CI-02: ese contrato vivo solo automatiza la generación de los mocks más adelante. Sin datos reales.»

**Terminada cuando** (Jira): (a) la app corre una pantalla de la maqueta contra la API simulada; (b) cambiar a la API real es solo cambiar la URL de configuración; (c) hay una prueba que compara los mocks con el contrato de la §4. El criterio (b) queda cumplido en diseño y su texto en Jira lo ajusta el líder (§8 D2).

Qué entrega este repositorio (§8):
- Una **capa de red mínima** en `app/lib/core/red/`: una interfaz `ClienteApi` (petición → respuesta con estado, encabezados y cuerpo), una **configuración** leída de `--dart-define` y un **proveedor** único (`clienteApiProvider`) que es el punto de inyección: en modo simulado entrega la simulación y en modo real falla de forma explícita hasta que TT-MOB-03 traiga el cliente generado.
- Una **API simulada en memoria** (`ClienteApiSimulado`) con respuestas JSON ficticias para tres contratos de la §4: `GET /api/v1/oficios`, `POST /api/v1/auth/firebase` y `GET /api/v1/colonias/en-punto`, incluidos sus errores 4xx y 5xx por **escenario**.
- La **pantalla de oficios** de TT-PRU-02 conectada a la API: un `OficiosRepositoryApi` en `features/oficios/data/` y el cambio de una línea en `oficios_providers.dart` (lo que la spec de TT-PRU-02 dejó previsto).
- Una **tabla de contrato versionada** derivada a mano de la §4 de cada spec (`app/test/contrato/contrato_s4.json`) y la prueba que compara cada mock con ella.

**Qué ya existe** (leído en `app/` de esta rama; `python scripts/codemap.py --query "red cliente api http"` sin coincidencias): `core/errores/failure.dart` (`Failure` sellado con `DatosInvalidosFailure` y `ServicioNoDisponibleFailure`), `core/red/` vacía (solo `.gitkeep`), la feature `oficios` completa con `OficioMapper.listaDesdeContrato`, `OficiosRepositoryDePrueba` y `oficiosRepositoryProvider` (raíz de composición), y `flutter_riverpod` 3 y `go_router` como únicas dependencias. **No existen** en este repositorio `contracts/openapi.v1.json`, `app/packages/knock_api/`, `scripts/sync_contract.py` ni `scripts/gen_clients.sh` (los cita `AGENTS.md` §2, pero aún no están), ni `dio`.

**TT-MOB-08** — Como persona del equipo que construye la app, quiero que la app consuma una API simulada con la forma exacta de la §4 de las specs del backend, para avanzar las pantallas sin esperar a que el endpoint real esté publicado y cambiar a la API real solo con la URL.

**Datos de prueba.** Solo datos ficticios: los tres oficios del ejemplo de la §4 de TT-PRU-01 (`ele`, `mec`, `plo`), una colonia inventada («Colonia Simulada Centro», CP `00000`, municipio «Municipio de Prueba», `id` `000000000000000000000001`), coordenadas de ejemplo sin relación con una persona y tokens con la forma `simulado-access-…`/`simulado-refresh-…` (no son JWT, no se firman y no se guardan). ## 5. Modelo de datos
Sin persistencia (ni local ni en servidor). Valores en memoria:
- `ConfiguracionApi { modo: simulado | real, baseUrl: Uri? (solo origen), escenario }`. Claves de `--dart-define`: `KNOCK_API_URL` (origen sin ruta, p. ej. `https://api.ejemplo.invalid`; vacío = simulado fuera de release) y `KNOCK_API_ESCENARIO` (solo simulado): `normal` (por defecto), `vacio`, `error_servidor`, `sin_conexion`, `lento`, `no_autorizado`, `fuera_de_cobertura`, `limite` y, solo para `auth/firebase` (D13), `cuenta_existente`, `cuenta_suspendida` y `conflicto_de_cuenta`. Un escenario que no aplica a un endpoint deja ese endpoint en `normal`.
- `PeticionApi { metodo, ruta, consulta (lista de pares, para detectar parámetros repetidos), encabezados, cuerpo? }` y `RespuestaApi { estado, encabezados, cuerpo (texto) }`. El cuerpo viaja como texto JSON para que el repositorio lo decodifique igual que una respuesta real.
- `ErrorDeRedApi` (sin conexión o tiempo agotado): no guarda URL, consulta ni cuerpo. `ErrorDeConfiguracionApi` (URL no permitida, release sin URL, modo real sin cliente real): no repite el valor recibido.
- `Failure` (existente) + `SolicitudRechazadaFailure { estado }` (D7).
- Tabla `contrato_s4.json` (solo pruebas): por endpoint y estado, `contentType`, esquema reducido (`type`, `required`, `properties`, `additionalProperties: false`, `nullable`, `maxLength`, `pattern`, `items`) y `fuente { repo, rama, commit, spec }`.

| Amenaza | Control | Caso que lo prueba |

**Decisiones** (las que respondió el líder en el PR #45, 2026-10-28, dicen «Resuelto»; las demás quedan como propuesta de quien redacta):
- **D1 — Cómo se sirve la API simulada.** **Resuelto: en memoria, dentro de la app**, como una implementación de `ClienteApi` en `app/lib/core/red/simulada/`. Porqué: no agrega dependencias, no necesita levantar un proceso aparte ni configurar Android para texto claro, funciona igual en `flutter test`, en el CI y en el emulador, y los escenarios de error se eligen con `--dart-define`. Alternativas descartadas: (a) **servidor local** en Dart puro (`dart:io` `HttpServer`) en `app/tool/api_simulada/`: es HTTP de verdad y lo podría usar también el panel, pero hay que arrancarlo, usar `10.0.2.2` o `adb reverse` y permitir texto claro en el `debug` de Android; (b) **adaptador de `dio` en memoria** (`HttpClientAdapter`): encaja directo con el cliente generado de TT-MOB-03, pero exige agregar `dio` ahora, antes de que TT-MOB-03 lo evalúe. TT-MOB-03 adapta la simulación (D8).
- **D2 — Cliente HTTP (principio 4).** **Resuelto: no se acepta la excepción al principio 4.** Nada de llamadas HTTP escritas a mano, ni siquiera temporales; el cliente real lo trae TT-MOB-03 con el cliente generado. En consecuencia se eliminó el caso del cliente HTTP y la prueba de cambio de URL pasó a TT-MOB-03; los casos siguientes se renumeraron. El criterio (b) de Jira queda cumplido en diseño: `clienteApiProvider` ya distingue simulado y real. El texto de ese criterio en Jira lo ajusta el líder.
- **D3 — Configuración de la URL.** **Resuelto: solo `--dart-define`** (`KNOCK_API_URL`, `KNOCK_API_ESCENARIO`), sin flavors de Android/iOS por ahora y **sin ninguna URL real en el repositorio** (no existe una todavía; el único entorno de Azure sale de `main`, constitución §9). Sin URL se usa la simulación en debug, y en release siempre falla. Con URL real y sin cliente real también falla de forma explícita, sin caer a la simulación. La ficha de TT-MOB-03 habla de flavors dev/staging/prod; Staging ya no existe (constitución 2.2.0), así que si se quieren flavors los define TT-MOB-03. `KNOCK_API_URL` es el **origen** (esquema, host y puerto); las rutas `/api/v1/…` las pone cada repositorio, como en la §4.
- **D4 — Cómo se escriben los mocks.** *Propuesta:* como **texto JSON literal dentro de constantes de Dart** en `core/red/simulada/respuestas_simuladas.dart` (no como assets: no cambia `pubspec.yaml` y no se empaquetan archivos sueltos), con datos ficticios. El texto se decodifica con `jsonDecode` igual que una respuesta real. La selección del modo simulado va detrás de `kReleaseMode` constante, para que el compilador pueda quitar la simulación de la build release (no se verifica en esta tarea; ver límites).
- **D5 — Prueba que compara mocks con el contrato.** *Propuesta:* una **tabla versionada** `app/test/contrato/contrato_s4.json` escrita a mano desde la §4 (un subconjunto de JSON Schema: `type`, `required`, `properties`, `additionalProperties`, `nullable`, `maxLength`, `pattern`, `items`) con la fuente y el commit por endpoint, y un validador pequeño en la propia prueba (sin dependencias). No se pone en `contracts/` (es del contrato vendorizado y no se edita a mano). Cuando exista `contracts/openapi.v1.json`, la prueba pasa a leer los esquemas de ahí y la tabla se borra.
- **D6 — Pantalla de la maqueta.** **Resuelto:** la de **oficios** de TT-PRU-02, porque ya existe con sus cuatro estados y su spec dejó previsto el cambio en un solo proveedor. `OficiosRepositoryDePrueba` **se conserva** sin cambios porque lo usa la prueba `TC-TT-PRU-02-07` (spec Aprobada); solo deja de estar en el proveedor. Borrarlo queda para cuando se cierre TT-PRU-02 o llegue TT-MOB-03.
- **D7 — Errores 4xx y 5xx.** **Resuelto: se agrega `SolicitudRechazadaFailure` ahora; TT-MOB-03 lo adapta.** Traducción mínima por estado en `data/`: red, tiempo agotado y `5xx` → `ServicioNoDisponibleFailure`; `4xx` → `SolicitudRechazadaFailure { estado }` (subtipo nuevo del `Failure` sellado; la pantalla de oficios ya trata cualquier error igual); cuerpo fuera de contrato → `DatosInvalidosFailure`. La lectura de ProblemDetails y el catálogo de mensajes son de TT-MOB-03.
- **D8 — Relación con TT-MOB-03 (no duplicar).** `clienteApiProvider` es el único punto de inyección: TT-MOB-03 conecta ahí el cliente real, quita el error del modo real y decide si la simulación pasa a ser un adaptador de `dio` que reutiliza las mismas respuestas y la misma prueba de contrato, y si los repositorios pasan de `ClienteApi` a los métodos del cliente generado (ese cambio sí toca `OficiosRepositoryApi`; el criterio «solo cambia la URL» se refiere a simulado ↔ real, no a la migración al cliente generado).

- **D11 — Backend local por HTTP en el emulador.** Android bloquea el texto claro por defecto; apuntar a `http://10.0.2.2:<puerto>` necesitaría un `network_security_config` solo para `debug`. *Propuesta:* fuera de esta tarea (no hace falta para la simulación); si alguien lo necesita, va en una tarea propia o en TT-MOB-03.
- **D12 — Escenario por `--dart-define` y en pruebas.** En la app el escenario es global (uno por ejecución); en pruebas, `ClienteApiSimulado` acepta el escenario por constructor o por un proveedor sobreescribible, para poder cambiarlo entre la primera petición y Reintentar (caso 09).

**Límites conocidos:**
- La prueba de contrato compara contra una tabla escrita a mano desde la §4: si una spec del backend cambia su §4 y nadie actualiza la tabla, la prueba no lo detecta. El commit de origen en cada fila hace visible la desactualización, y la automatización es TT-CI-02.
- No se verifica que la simulación quede fuera de la build release (habría que inspeccionar el APK release; el CI solo compila `debug`).
- Hasta que llegue TT-MOB-03 la app no puede apuntar a la API real, y una compilación release no arranca (con o sin URL).
